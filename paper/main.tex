\begin{abstract}
The simplest way to obtain an exam from teaching material today is to upload the document to a
chat-based large language model (LLM) and ask for a test. This gives no evidence that the keyed
answers are supported by the document, no control over which parts of the material are covered,
and it sends the material to a third party. We present \Mimir{}, an open system that generates
multiple-choice exams from a teacher's own documents with a small language model running on a
consumer GPU. \Mimir{} replaces the single prompt by an explicit method: semantic chunking, a
\emph{blueprint} that assigns concepts, question types and Bloom levels to slots, per-question
generation with chunk citations, and a verifier chain that checks grounding, distractors, blind
answerability and answer leakage before a mandatory human review. Uploaded content is kept only for the
duration of a job. We also contribute an evaluation methodology: fourteen single-factor arms, a 39-document Hungarian
and English dataset, a cross-family LLM judge and document-level statistics. A pilot exposed a malformed
fallback and an answer-leakage failure mode that fooled the verifier and the judge. In the main study
(nine documents, six per arm, 1{,}670 questions), the planned and verified pipeline on a 4-bit 7B model
reached a quality index of 0.96 (95\,\% CI 0.93--0.98), against 0.64 for naive RAG, 0.83 for the whole
document in one prompt to the same model and 0.95 for the whole document to a large server model, which
reached 0.99 with our pipeline. Planning added 0.24 and verification 0.08; another-family verifier and a
concept graph did not help; the verifier's flag agrees only weakly with the judge ($\kappa\le0.22$); and
with six documents no difference survives Holm correction.
\end{abstract}

\section{Introduction}

Writing good multiple-choice questions is slow: the stem must be unambiguous, exactly one option must
be correct according to the course material, and the distractors must be plausible but provably
wrong. Large language models (LLMs) can draft such questions~\cite{kurdi2020systematic,alhazmi2024distractor},
and the most common way teachers use them is direct: upload the lecture notes to a chat assistant and
ask for ``ten multiple-choice questions''. This is convenient, but it has four weaknesses that matter
in a school.

\textbf{(P1) Correctness is not checked.} Nothing verifies that the keyed option is supported by the
document or that the distractors are actually false; LLMs produce plausible but unsupported
statements, which self-verification can reduce but not remove~\cite{madaan2023selfrefine,dhuliawala2024cove}.
\textbf{(P2) Structure and coverage are not controlled.} The requested number, types and difficulty
of questions are only suggested in the prompt, and long inputs are used unevenly---models attend to
the beginning and end of long contexts more than to the middle~\cite{liu2024lost}---so questions
cluster on a few sections. \textbf{(P3) Privacy.} Teaching material may contain personal data, and a
hosted assistant makes the provider a recipient of it. \textbf{(P4) Dependence on large hosted models.}
Whole documents need long contexts and large models; the small models a school can run itself have
limited context and memory.

\Mimir{} addresses these with a method rather than a prompt, and runs it on a single consumer GPU.
We ask three research questions:
\begin{itemize}
\item[\textbf{RQ1}] Does structured generation---planning, per-question grounding and
verification---produce more valid and better-covering exams than prompting a model with the document?
\item[\textbf{RQ2}] What does each component contribute, and what does it cost in time and model calls?
\item[\textbf{RQ3}] How close does a 7B model on an 8\,GB consumer GPU come to a large server-hosted model?
\end{itemize}

\textbf{Contributions.} (1) The \Mimir{} generation method: semantic chunking, a coverage-driven
exam blueprint, cited per-question generation and a verifier chain (Section~\ref{sec:method}).
(2) A privacy-preserving local deployment with zero retention of uploaded content and a measured
GPU footprint that fits an 8\,GB card (Section~\ref{sec:privacy}). (3) An evaluation methodology and
open harness: fourteen single-factor arms, a bilingual dataset with reference questions, a cross-family
judge and document-level statistics (Section~\ref{sec:eval}). (4) Results of a pilot, which exposed
measurement defects, a malformed fallback and an answer-leakage failure mode, and of a 14-arm main study
on nine documents (Section~\ref{sec:results}).

\section{Related Work}

\textbf{Question and distractor generation.} Surveys of educational question
generation~\cite{kurdi2020systematic} and distractor generation~\cite{alhazmi2024distractor} note that
evaluation often relies on reference-overlap metrics or small human studies that rarely verify answer
correctness. Small models can produce comparable educational questions after further pre-training
and fine-tuning~\cite{fawzi2023small,fawzi2024towards}, and small private models have been compared
with large ones for Bloom-aligned assessment design~\cite{jaldi2026small}. We use off-the-shelf models
without fine-tuning and add explicit grounding and verification.

\textbf{Retrieval and long contexts.} Retrieval-augmented generation (RAG) grounds output in retrieved
passages~\cite{lewis2020rag}; hybrid retrieval fuses BM25~\cite{robertson2009bm25} with dense
embeddings~\cite{wang2024me5} using reciprocal rank fusion~\cite{cormack2009rrf}, and graph-based
RAG builds a concept graph for questions that need global context~\cite{edge2024graphrag}. Long-context
prompting, the alternative, uses the middle of the input poorly~\cite{liu2024lost}.

\textbf{Verification and small models.} Iterative self-feedback~\cite{madaan2023selfrefine} and
verification questions~\cite{dhuliawala2024cove} reduce factual errors, and spending inference compute
can substitute for model size~\cite{snell2025scaling}. Quantised 4-bit models lose little accuracy on
general benchmarks~\cite{li2024evalquant,kurtic2025bf16}, which makes local deployment plausible.

\textbf{LLM judges and languages.} LLM judges correlate with humans~\cite{zheng2023judge} but favour
their own family~\cite{panickssery2024selfpref}. For Hungarian, benchmarks~\cite{ligetinagy2024hulu}
and QA data~\cite{novak2023milqa} exist, but we know of no evaluation of exam generation.

\textbf{Document processing.} Text is extracted from PDF, DOCX or plain text and split into semantic
chunks: sentences are embedded with multilingual E5~\cite{wang2024me5}, and a cut is placed where the
cosine distance between neighbouring sentences exceeds a percentile (or mean\,+\,$k\sigma$) threshold,
within a target size. The encoder works in windows of at most 512 tokens (Section~\ref{sec:validity}).
Chunks are indexed in a vector store that exists only for the current job.

\textbf{Blueprint.} One call proposes $n+3$ concepts that cover the document, each with the chunk
identifiers that support it. Slots are filled greedily, preferring concepts that touch chunks no slot
covers yet, so the exam spreads over the document; the three spare concepts serve as replacements.
Each slot receives a question type and a Bloom level~\cite{anderson2001bloom} by largest-remainder
allocation from a difficulty-dependent mix (easy: remember/understand; medium:
understand/apply/analyse; hard: apply/analyse/evaluate). Count and types are therefore guaranteed by
construction (G2).

\textbf{Grounded generation.} For each slot, the concept's chunks are combined with the top-$k$
retrieved passages (dense, or BM25 and dense fused with RRF), and the model writes \emph{one}
question that must cite the chunk identifiers supporting its key (G1). A concept-graph variant (E3)
extracts concepts and typed relations per 3{,}000-character batch, replaces the planner call with graph
concepts, offers sibling concepts as distractor ideas, and adds 1-hop neighbour chunks to the context.

\textbf{Verification.} Checks run cheapest first (Table~\ref{tab:verifier}). A failed check returns its
reason to the generator for one retry; after that the slot moves to a spare concept, and as a last
resort the best attempt is kept and flagged as unverified for the teacher. Near-duplicates (embedding
similarity $>0.9$) are regenerated. After the pilot we added leakage checks, a repair call for malformed
last-resort questions, and an optional verifier from another model family.

\textbf{Human review.} The draft opens in an editor where the teacher can edit, reorder, change the
key, regenerate a single question and view each question's cited source passage. Nothing is exported
without approval, and the exported PDF states that the content was drafted with an AI system and by
which model (G5).

\section{Privacy and Local Deployment}
\label{sec:privacy}

\textbf{Zero retention (G3).} Uploaded bytes, extracted text, chunks, embeddings and prompts exist only
in service memory for the duration of a job; the vector store is cleared when the job ends or fails,
and job results expire after 60 minutes. The audit log keeps the job identifier, model, prompt version,
quality score and SHA-256 fingerprints and lengths of the request and context---never content. A
\texttt{LOCAL\_ONLY} switch disables every external model call; otherwise the upload screen names where
the document will be processed and lets the teacher choose the local model.

\textbf{Consumer GPU (G4).} The generator is Qwen2.5-7B~\cite{qwen25} with 4-bit (Q4\_K\_M) weights in
the Ollama runtime, the only thing on the GPU; embeddings and all services run on the CPU. Because every
call in the blueprint pipeline is short, the context stays at 8{,}192--16{,}384 tokens; the 7B model's
grouped-query attention needs 56\,KiB of key--value cache per token, about 0.9\,GB at 16{,}384 tokens.
In the pilot, GPU memory rose from 1.6--1.9\,GB (desktop, model not yet loaded) to a peak of
7.0--7.8\,GB during generation, so the model and runtime occupied 5.4--5.9\,GB---within the budget of
an 8\,GB card, including the desktop. Table~\ref{tab:budget} estimates the budget for other local
models: 3--8B models at 4 bits fit 8\,GB; a 4-bit 14B model or an 8-bit 7B model needs 12\,GB.

\section{Evaluation Methodology}
\label{sec:eval}

The harness (\texttt{tests/eval}) runs in three steps: \emph{run} generates exams for every
document$\times$seed of an arm, \emph{score} computes metrics and calls the judge, and \emph{report}
produces tables, tests and figures. Each run stores its configuration, git commit and dataset version.

\textbf{Dataset.} Table~\ref{tab:dataset} summarises the 39 documents, frozen as \texttt{eval-v1}.
EduQG~\cite{hadifar2023eduqg} and MILQA~\cite{novak2023milqa} importers select short, medium and long
documents and keep reference questions whose evidence sentence occurs in the document; references are
used for retrieval recall and similarity, not as targets.

\textbf{Measures.} \emph{Format compliance} is 1 if an exam has exactly the requested number and shape
of questions. Per question, the judge decides \emph{grounding} (the source supports the key, with a
quoted sentence), \emph{distractor validity} (each distractor false and on topic) and \emph{blind
answerability} (answering from the source without the key picks the keyed option), and gives 1--5
rubric scores. The \emph{quality index} is the mean of these four rates. \emph{Coverage} is the share
of the document's chunks that are the closest chunk (by embedding) of at least one question; we also record duplicates,
meta-references, answer leakage, unverified questions, calls, tokens, time, peak GPU memory, the GPU
model and the share of the model held in GPU memory.

\textbf{Judge and teachers.} The judge is gpt-oss-120b~\cite{gptoss2025}, from a different model family
than the generators, to avoid self-preference~\cite{panickssery2024selfpref}. It sees the chunks each
question was written from or, for whole-document arms, the first 24{,}000 characters of the document. Blind teacher rating
sheets use the same rubric; Krippendorff's $\alpha$~\cite{krippendorff2004} and Spearman's $\rho$
validate the judge.

\textbf{Statistics.} Documents are the unit of analysis: measures are averaged over questions and seeds
per document, with 10{,}000-resample bootstrap CIs~\cite{efron1993}, paired Wilcoxon
tests~\cite{wilcoxon1945} with Holm correction~\cite{holm1979}, and rank-biserial effect
sizes~\cite{kerby2014}. Fewer than six documents cannot reach $p<0.05$, so single-document results are
reported descriptively.

\subsection{Measurement validity}
\label{sec:validity}

Building the harness exposed two defects that had made earlier end-to-end measurements invalid.
\emph{Fallback exams counted as results:} when every model call failed, the backend returned a
hard-coded one-question exam, which a test run on 3 May 2026 reported as three documents generated in
4--9\,s; it is now counted as a failure. \emph{Truncated chunking:} the chunker embedded each document in
one 512-token pass, so every sentence after roughly the first page received a zero vector---an estimated
68--71\,\% of the average \texttt{eval-v1} document. The encoder now works in windows; arm E5a keeps the
old one. A third issue, answer leakage, was found in the pilot.

\section{Results}
\label{sec:results}

\subsection{Pilot}

The pilot ran ten arms on one short Hungarian text (1{,}702 characters, 4 chunks) with three seeds,
on a consumer GPU (NVIDIA GeForce RTX 3070 Ti, 8\,GB). Four findings changed the main study.
\emph{Noise:} E0 and E5a received identical chunks, context and seeds yet scored 0.83 and 0.90, so on one
document differences below about 0.07 are noise. \emph{Malformed fallback:} in one exam of every verifier
arm a kept last-resort question had only two or three options, which zeroed that exam's format compliance;
verification then lowered the index (E1 0.88, E2 0.76). \emph{Self-verification at chance level:}
questions the 7B verifier passed were judged grounded less often (66\,\%) than those it flagged (75\,\%;
$\kappa$ from $-0.14$ to $0.07$). \emph{Answer leakage:} the verifier's feedback loop pushed the small
model towards copying a source sentence into the stem and repeating it as the key, the cheapest way to pass
a grounding check. In 20\,\% of the concept-graph arm's questions the key's words appeared in the stem
($\ge$80\,\% token overlap)---e.g.\ a stem quoting that coffee reached Europe in the 17th century, keyed
with the same sentence and distractors naming other centuries---and the judge rated such items 5 of 5. The main study
therefore keeps only well-formed last-resort questions (with one repair call), rejects stems that contain
the key or are not questions (Table~\ref{tab:verifier}), and reports leakage.

\subsection{Main study}

\textbf{Setup.} The main study ran on 27--28 September 2026 with the corrected pipeline and one retry
per slot. It covers nine of the 39 documents, six per arm. Twelve arms---all local arms and B-doc-S---ran
on the three short Hungarian teaching texts (1{,}696--2{,}295 characters) and a short, a medium and a long
OpenStax text (6{,}000, 24{,}937 and 68{,}063 characters); E4 and E4b ran on six English OpenStax
documents, three of them shared with the others. Single-call arms used three seeds, planned arms one:
1{,}670 questions, all judged; teacher ratings are not yet in. With six documents, $p<0.05$ requires all
six differences to share a sign.

\textbf{Method versus prompting (RQ1).} On the shared six documents, the planned and verified pipeline on
the local 7B model (E2) scored 0.96 (CI 0.93--0.98), against 0.64 for naive RAG (E0) and 0.83 for the whole
document in one prompt to the same model (B-doc-L). B-doc-L failed the format in 17\,\% of its exams and saw
only the first 30{,}000 characters of the longest document. Given the whole document, the server model (B-doc-S) reached 0.95, as high as the
local E2. Coverage did not separate the method from whole-document prompting (B-doc-L 45\,\%, B-doc-S
47\,\%, planned arms 40--45\,\%); the clustering seen in the pilot reappeared only with naive RAG (E0
25\,\%, E4 9\,\%).

\textbf{Components (RQ2).} Planning (E1) raised the index of naive RAG by 0.24 ($r=0.62$), grounding from
43 to 80\,\%, distractor validity from 52 to 91\,\% and coverage from 25 to 45\,\%, at 17 calls and
1.9~minutes per exam---but only on the English documents (0.40$\to$0.91; Hungarian 0.88$\to$0.85). Unlike in
the pilot, verification (E2) improved on planning on every one of the six documents ($+0.08$, $r=1.00$,
unadjusted $p=0.031$, Holm 0.19): grounding rose from 80 to 90\,\% and blind answerability from 80 to
97\,\%, at 51 calls and 3.5~minutes per exam, and every verifier arm now had 100\,\% format compliance.
Dropping the blind-answer test (E2f, 0.90) or adding hybrid retrieval (E2h, 0.92) did not help. The
Llama-3.1-8B verifier (E2x) passed 75\,\% of the questions instead of 52\,\% and lowered the index to 0.89
($r=-0.90$); the concept graph (E3) lowered it to 0.88, mainly through weaker distractors (83 vs.\
96\,\%).

\textbf{The verifier as a classifier.} The pilot's direction reversed: of 360 questions in the six
verifier arms, those the verifier passed ($n=234$) were judged grounded more often (89\,\%) than those it
flagged ($n=126$, 77\,\%), and the judge would use 85 vs.\ 68\,\% of them; without E4b, whose server verifier passed all 60
questions, 150 of the 174 passed local questions (86\,\%) were grounded. Agreement stayed weak, with
$\kappa$ from 0.02 to 0.22 for the local verifiers: precision 0.79--0.94 but recall 0.54--0.79, so about
three quarters of the flagged questions are in fact sound. The flag is a useful warning, not a verdict.

\textbf{Leakage and degenerate questions.} The rule checks removed most leakage from the verifier arms
(key in stem 0--3\,\%; E3 0\,\% against 20\,\% in the pilot); statement stems are now most frequent with
fixed-size chunks (E5c, 41\,\%) and in B-doc-L (17\,\%). A new failure appeared with naive RAG on the server
model: E4 asked about the retrieved text itself (``How many words are in Link to Learning?''), and the
judge rated such items 5 of 5. They inflate E4's index (0.91) and fit its 9\,\% coverage.

\textbf{Naive RAG is fragile.} The chunking arms show why E0 was weakest. On the Hungarian texts the
semantic variants scored 0.87--0.89, but on the English documents E0 and E5b collapsed (0.40 and 0.51,
grounding 0\,\%), while the legacy encoder (E5a, 0.87) and fixed 800-character chunks (E5c, 0.96) did not.
OpenStax texts contain short structural lines (``Link to Learning'') that semantic chunking, having no
minimum chunk size, turns into chunks of their own, and the naive query---a task description such as
``10 multiple-choice questions''---lands on them: the judge saw contexts that were a heading or no words. Retrieval itself was sound (recall@3 of the
reference evidence 89--95\,\% in every arm), and the planned pipeline, which searches per concept, was
unaffected (E1 0.91 on the English documents).

\textbf{Server versus local (RQ3).} On the three documents shared by all arms, the local E2 scored 0.95

\section{Discussion}

\textbf{Why a method rather than a prompt.} The same 7B model went from 0.64 (naive RAG) and 0.83 (whole
document) to 0.96 once the exam was planned and verified; naive RAG depended on chunking details that a
per-concept search avoids; and per-question citations let the judge---the teacher, in practice---check
each key, which exposed wrong keys, leakage and degenerate questions. On these mostly short documents,
however, the whole-document server baseline was as good and covered as much, so the case against hosted
models rests on verifiability, privacy and local operation (P1, P3, P4), and the coverage argument (P2)
holds against naive RAG only. We recommend E2 as the local configuration, with the verifier's flag shown
as a warning.

\textbf{What the main study does not show yet.} It covers nine of the 39 documents, six per arm; its
Hungarian part is three short texts and no Wikipedia article, so language is confounded with source and
length; E4 and E4b ran on partly different documents; planned arms used one seed; and no comparison
survives Holm correction. The judge is not yet validated by the teachers
(\tbd{teacher ratings: Krippendorff's $\alpha$ and judge--teacher agreement}). The next run puts the core
arms on all 39 documents with identical document sets, gives the judge the full document for
whole-document arms, and measures a minimum chunk size for naive RAG.

\textbf{Reproducibility.} Every run stores its configuration, git commit, dataset version and generator
settings; judge answers are cached, so re-scoring is deterministic; the run$\to$score$\to$report flow is
covered by end-to-end tests with a mock LLM; and the report writes Tables~\ref{tab:main}
and~\ref{tab:sig}. The pilot's raw outputs and both reports are released with the code.

\textbf{Limitations.} The judge sees each question's cited context and may miss contradictions elsewhere;
it rated leaking and degenerate questions highly. For whole-document arms it sees at most the first
24{,}000 characters: on the 68{,}063-character law document it judged B-doc-S's question on the ``access
economy'' unsupported because the term first appears at character 38{,}603, so whole-document grounding on
long documents is a lower bound. Only multiple-choice questions are evaluated. Run times (local GPU of the main run:
\tbd{model}; a shared server) are indicative only.

\section{Conclusion}

\Mimir{} turns exam generation from a single prompt into a verifiable method that runs on a consumer
GPU without retaining teaching material. In a main study on nine documents, the planned and verified
pipeline on a local 7B model scored 0.96, against 0.64 for naive RAG and 0.83 for the whole document in one
prompt to the same model, and matched a large server model given the whole document (0.95); on the server
model the same pipeline reached 0.99. Planning and verification helped, a verifier from another family and
a concept graph did not, and the verifier's per-question flag agrees only weakly with the judge. Building
the evaluation exposed failure modes that inflate automatic and LLM-judge scores. The full 39-document run with teacher ratings
will test these findings; code, configurations, dataset manifests and reports are released.
